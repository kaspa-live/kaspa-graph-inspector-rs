# KGI v2 pre-handoff reconciliation

This report was reconstructed in the original KGI v2 chat. It covers decisions and discussions from the 17 September 2026 handoff through creation of the 20 September 2026 handoff, and records their state at the end of that interval. Later Architecture-chat decisions are outside its scope and must be reconciled separately.

This is a **decision ledger for the conversation between the two handoffs**, not a summary of either handoff. The September 17 handoff is the baseline; “Clarified” generally means a rule was already present there but acquired a sharper contract during review. Coverage was compared against the **original committed September 20 handoff** (`31c33cc`). The working-tree copy was subsequently edited, so its current text is not the historical comparison target.

The decisions below come from the original KGI v2 chat. Repository documents were used to check the baseline and handoff coverage. Coverage means **Yes** (accurately present), **Partial** (present without an important qualification), **Missing**, or **Conflict** (incompatible wording).

Document shorthand in the tables: [O: overview](docs/architecture/overview.md), [L: processing lifecycle](docs/architecture/processing-lifecycle.md), [B: block processing](docs/architecture/block-processing.md), [V: VSPC processing](docs/architecture/vspc-processing.md), [N: node service](docs/architecture/node-service.md), [S: storage](docs/architecture/storage.md), [F: future work](docs/future-work.md), and [H: September 20 handoff](docs/architecture/handoff-2026-09-20.md). “API” denotes the API contract presently concentrated in H §13–18 rather than a dedicated focused document.

## Material discrepancies and work left by the September 20 handoff

The audit did **not** treat the handoff’s word “settled” as sufficient where the original conversation retained a qualification or an unanswered question. These items require explicit reconciliation in the Architecture chat:

1. **VSPC destination invariant versus removed-only fallback.** The interval settled that an admitted nonempty `VspcChange` has a destination in `added.last()`, while acknowledging that impossibility of an upstream removed-only notification was not formally proved. The original September 20 handoff §9 still offered a fallback for removed-only changes. These cannot both be the normative v2 input contract. The proof and policy for such a notification remain open; the no-destination pathological case is deferred.

2. **Catchup crossing and normalization.** The design rejected requiring notification destination to equal synthetic sink; a notification may cross. But normalizing its actionable suffix requires demonstrating the committed synthetic sink inside the notification’s added sequence. The later handoff records crossing generally without stating that exact proof condition or the complete raw/resolved pending-index structure.

3. **VSPC duplicate-transition disposition.** The chat changed “discard a second identical notification idempotently” to **Resync on invariant violation**. The later handoff does not make this specific rule explicit enough to prevent reintroducing the rejected behavior.

4. **Rebuild fault precedence.** The broad point-6 rule said only ResyncEngine’s failed reconciliation can request Rebuild, while later resolver/VSPC discussions entertained missing materiality as Rebuild-worthy. The audit could not resolve this from the interval itself. A subsequent explicit Architecture decision now requires direct Rebuild for nonmaterialized VSPC chain members and resolver-confirmed unavailable dependencies; the current handoff records those exceptions.

5. **Lifecycle milestone wording.** The handoff covers `PpBoundarySealed` and Live, but the reviewed distinction between command enqueue, completed teardown/pump barrier, and workers’ queued data should be retained. In particular, `EnteredLive` does not certify empty worker queues or zero orphans.

6. **API Reset protocol detail.** Reset-before-DB-reinitialization was accepted; the exact producer/API acknowledgement mechanism and in-flight read behavior are still implementation-contract work, not permission to serve mixed epochs.

7. **Sizing and representation choices.** Exact `MAX_WINDOW_DEPTH`, orphan-store capacity, API/SSE client caps, throttle parameters, and graph wire format were not fixed. `MAX_CACHE_DEPTH = 1000`, bounded data paths, processing priority, and representation_version *were* fixed. Do not turn the open numbers or benchmark outcome into unstated defaults.

8. **Observational metadata.** `network_id` and `db_pp_blue_score` are correctness metadata. Last-observed node/version persistence and Web delivery remain API design work; neither is a recovery decision input.

9. **v2.1 candidates already identified.** Keep a future-work record for a low-frequency Live VSPC consistency probe, an administrative recovery API, offline v1→v2 database import, deterministic/canonical slot ordering, and historical graph-result caching. These do not block v2. Their detailed contracts have not been settled.

10. **Scope of this ledger.** It records what was decided *between* the two handoffs, including rejected intermediate proposals. It does not claim to supersede later decisions made in the separate Architecture chat. Reconcile those later decisions against this historical state before turning any discrepancy into implementation work.

### Deliberately unresolved implementation choices

The review did not fix the Cargo crate/module split; PostgreSQL Rust client, concrete SQL types, and migration code; detailed bounded-channel sizes; orphan capacity and exact trigger within the one-quarter-to-one-third range; RPC concurrency, retries/backoffs, and cancellation/drain timeouts; Tokio fairness mechanics; cache memory and delta-history limits; exact HTTP route names/schema; SSE connection cap; adaptive fixed-view throttle curve; metrics/tracing/deployment; or the exact graph response format. It also left the mechanism for bounded API historical-read cancellation/locking around Reset open. Those are implementation choices, not licenses to weaken the settled invariants above. A coherent new API image must exist before historical reads reopen after Rebuild; whether that occurs in PostSeal or at Live was not selected.

### Rejected approaches to keep out of the v2 implementation

The conversation explicitly rejected a monolithic block-plus-VSPC worker; committed-block-index waiters; materialized placeholder blocks and later promotion; persisting ordinary orphan hashes; `Auto` recovery; broad notification epochs or a router/transport fence; timer-based latecomer grace; VSPC rewind/replay; source-blind VSPC commitment; fixed unordered-sink capacity or tenfold merge-set estimate as the Catchup trigger; a fixed X/Y overlap requirement; an empty-orphan Live prerequisite; extra `ProcessingResources`, `ReadyAddedBlock`, and `PendingVspcChange` wrappers; parent-row FKs inferred merely from hash identity; a dedicated persisted VSPC checkpoint table; public CompactIds; cross-instance coordinate identity; partial HGC levels; API observer failure causing processing recovery; serving a partially rebuilt DB; and Supervisor-owned PP/reconciliation logic. Their rejection is part of this interval’s state even where a positive rule above already implies it.
