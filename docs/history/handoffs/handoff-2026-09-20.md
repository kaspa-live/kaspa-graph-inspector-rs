# KGI v2 architecture handoff — 20 September 2026

This document consolidates the accepted KGI v2 architecture through the API
review of 20 September 2026. It supersedes the 17 September handoff where
later decisions differ. Production code has not yet been implemented.

## 0. Reading rules and scope

This is the consolidated handoff for the Architecture, Implementation, and
Review chats. **Settled** statements are requirements. Rust and SQL fragments
are contract sketches, not a promise that those declarations compile. Exact
crate layout, capacities, locks, and library choices are not fixed unless
explicitly said. New decisions here supersede earlier focused documents where
they conflict; the September 17 handoff remains provenance.

| Superseded wording | Settled wording |
|---|---|
| `NodeClient` | `NodeService` |
| `ValidatedStorageService` | `ValidatedDbClient` |
| `Cycle 1` | `PreSeal` |
| prune VSPC history `<= sink` | prune entries **`< sink`**, preserving sink |
| `PendingVspcChange` wrapper | store `VspcChange` directly |
| API exposes CompactIds | response-local references plus hash dictionary |
| API deferred | in-process API is part of v2 |

The Rust rewrite covers KGI processing and API, using `rusty-kaspa` as node
reference, not Go `kaspad`. Go KGI and `simply-kaspa-indexer` are behavioral
references, not templates. Local-node gRPC bandwidth is not a design obstacle.
The subscription approach stays. Go KGI's `ProcessBlockAndDependencies` loads
dependencies recursively without a depth limit; do not repeat the erroneous
direct-parent-only description.

Architecture owns normative documents/ADRs; Implementation builds to them;
Review checks stable diffs and remains read-only unless authorized. The repo,
not chat, is durable truth. Conflicts between current code and accepted design
must be flagged, not resolved by quietly weakening either side.

## 1. System shape and ownership — settled

```text
Supervisor
├── Arc<NodeService> ───────────► Arc<ValidatedRpcClient> (one connection)
├── Arc<StorageService> ────────► Arc<ValidatedDbClient> (one DB generation)
├── Arc<ResyncEngine>
│   ├── Arc<BlockProcessor>
│   │   ├── OrphanManager
│   │   └── DependencyResolver
│   └── Arc<VspcProcessor>
└── Arc<ApiService> ────────────► HeadGraphCache

NotificationRouter (implements Notify)
├── BlockAdded ────────────────► BlockProcessor notification input
└── VirtualChainChanged ──────► VspcProcessor notification input

BlockProcessor ── PersistedBlock ──► OrphanManager, VspcProcessor
BlockProcessor/VspcProcessor ── ordered graph updates ──► ApiService
ResyncEngine ── Reset/PublishPostSeal/PublishLive controls ──► ApiService
```

Autonomous long-lived workers form a control tree. `ResyncEngine` owns both
processors and a run's `ProcessingSession`; `BlockProcessor` owns its children.
Parent commands child, child reports faults/milestones upward. Avoid strong
`Arc` cycles. `Arc<Component>` is a reasonable initial shape; thin handles
are not required. Notifications never pass through ResyncEngine. Each worker
serializes local state changes in one event loop despite concurrent inputs.
NodeService and StorageService own their respective service states;
ResyncEngine owns processing state; Supervisor owns orchestration state.
Their statuses are projections of those owners, not a second control state.

The API is in-process but observational and lower priority than processing.
A lost graph observer update invalidates/reloads the API, never stalls or
forces a processing resync solely to preserve HTTP freshness.

## 2. Shared identities and graph vocabulary — settled

```rust
type SharedNodeBlock = Arc<RpcBlock>;

#[derive(Clone, Eq, PartialEq, Ord, PartialOrd)]
struct ConsensusOrder { blue_work: BlueWork, hash: BlockHash }

struct VspcPoint { consensus_order: ConsensusOrder, id: CompactId }
struct BlockCoordinate { level: u64, slot: u64 }
struct MaterializedSyncAnchor { point: VspcPoint, blue_score: u64 }
```

`ConsensusOrder` sorts lexicographically by `(blue_work, hash)`. `VspcPoint`
contains this order and must not duplicate hash. Explicit `hash()`, `order()`,
and `id()` accessors are fine; not `Deref`. `CompactId` is an incremental
positive signed 64-bit **internal** identifier. Slot allocation order is not
cross-instance canonical: the same hash can have different coordinates in
different DBs.

Names are `level`, `slot`, `levels`, and `levels.size`, replacing Go's
`height`, `height_group_index`, and `height_groups`. Rebuilt PP is always
`(level=1, slot=0)`.

## 3. Lifecycle, intent, commands, and channels — settled

```rust
/// Ordering denotes recovery strength, never lifecycle/execution order.
#[derive(Ord, PartialOrd, Eq, PartialEq)]
enum RecoveryMode { Resync, Rebuild } // Resync < Rebuild

enum FaultDisposition { Retry, Require(RecoveryMode), Fatal }

enum Component {
    Supervisor,
    NodeService,
    StorageService,
    ResyncEngine,
    BlockProcessor,
    OrphanManager,
    DependencyResolver,
    VspcProcessor,
    ApiService,
}
enum ServiceKind { Node, Storage }
enum NotificationStream { BlockAdded, Vspc, Both }
enum RecoveryInputKind {
    RemovedOnlySyntheticVspc,
    MalformedGetBlocks,
    MalformedVspcResponse,
}
enum PersistenceFault {
    DefiniteFailure,
    RetryExhausted,
    AmbiguousCommit,
}
enum FaultKind {
    ServiceGenerationLost(ServiceKind),
    NotificationContinuityLost(NotificationStream),
    RecoveryInputInvalid(RecoveryInputKind),
    ReconciliationFailed,
    MaterialityViolation,
    DependencyUnavailable,
    Persistence(PersistenceFault),
    Ownership,
}
struct ComponentFault {
    source: Component,
    disposition: FaultDisposition,
    kind: FaultKind,
    diagnostic: Arc<str>,
}

struct SupervisorStatus {
    lifecycle: SupervisorLifecycle,
    desired_recovery: Option<RecoveryMode>,
    active_recovery: Option<RecoveryMode>,
}
```

`deactivation_requested` is internal, absent from public status. `SystemStatus`
combines Supervisor, NodeService, StorageService, and processing observations;
it is eventually consistent and never a synchronization or recovery input.

Normal startup requires Resync; `--clear-db` requires Rebuild. There is no
`Auto`. `desired_recovery` is the strongest **unsatisfied obligation**, not a
queued command; sending `Start` does not consume it. `active_recovery` is the
actual running mode. Requests coalesce by `max`. A stronger requirement
deactivates an active run once and waits for Idle. Resync reconciliation
failure reports `Require(Rebuild)` to Supervisor; the engine owns the
reconciliation logic. Two child-detected faults also request Rebuild
directly: a nonmaterialized hash directly in VSPC `added`/`removed`, and a
resolver-confirmed dependency unavailable from the node. In either case DB
contents can no longer be trusted against node state. An RPC/connection
failure is not a confirmed unavailable dependency. `Retry` is meaningful
only within recovery. It aborts and fully deactivates the current recovery
attempt; after Idle and backoff, Supervisor starts the strongest unsatisfied
`desired_recovery` from fresh preparation. `Retry` never repeats one RPC or
page in place. A Live recoverable fault needs at least Resync. Strings are
diagnostics, never control flow, so retry causes used by policy are typed.

`ComponentFault` is the concrete cross-worker control envelope. `kind`, never
`diagnostic`, drives retry counters, recovery policy, and metrics. Component
local errors may retain library-specific sources and richer variants; they
must be classified into this envelope before crossing an ownership boundary.
The enum sketch fixes the required semantic discriminants, not exact module
placement or error-library syntax.

For an active recovery `Retry` whose exact RPC and DB generations both remain
Ready, Supervisor applies nominal delays `1s, 2s, 4s, 8s, 16s, 30s`, then
stays capped at `30s`. Each actual delay uses equal jitter in the inclusive
range from 50% through 100% of its nominal value. Reset this general recovery
backoff on `EnteredLive`, acquisition of a new validated RPC or DB generation,
or a stronger recovery obligation. If a generation was lost, wait for its
service's own reconnect loop and do not add a second recovery delay.
`Require(Resync)` and `Require(Rebuild)` neither consume this Retry sequence
nor wait on it; after deactivation they proceed as soon as required resources
are usable. All timers and waits are lifecycle-cancellable.

One cause has a settled retry limit. A synthetic VSPC V2 response with empty
`added` and nonempty `removed` is impossible under the pinned upstream sink
monotonicity invariant. Supervisor owns a counter for that typed cause across
recovery attempts using the same `ValidatedRpcClient` generation. The first
three occurrences each abort the attempt with `Retry`; the fourth is `Fatal`.
Reset the counter only when a different validated RPC generation is acquired
or the system reaches `EnteredLive`. Mode changes on the same generation do
not reset it. A removed-only notification follows the separate
`Require(Resync)` rule and does not consume this pump-retry budget.
Its three permitted retries use the first three general recovery delay slots:
nominally `1s`, `2s`, and `4s`, with the same equal jitter.

The `--clear-db` obligation survives interruptions until a **definitely
committed** `PpBoundarySealed`. This is an upward milestone event, not a
command: BlockProcessor enters PostSeal and emits it to ResyncEngine, which
observes the seal, sends ApiService the PostSeal publication trigger, and
propagates the milestone to Supervisor. Supervisor then downgrades Rebuild
intent to Resync; Live clears the remaining obligation. Nothing sends the
milestone back to BlockProcessor. An ambiguous seal transaction must not emit
it. The next run rederives truth from persisted DB.

Command mailboxes are **unbounded and prioritized**, with one logical command
producer per worker; they do not apply data-channel backpressure. Data,
notifications, and worker-to-worker messages are **bounded and
cancellation-aware**. A full bounded channel means `Require(Resync)` if
session continuity was lost; closed/unavailable means session fault; send
cancellation during expected teardown is not a fault. The API observer feed
is exceptional: its loss invalidates the API image, not processing.
Faults and milestones travel on reliable owner-directed event paths; status
uses latest-value/watch semantics and may skip intermediate values. Each run
retains its first causal fault for diagnosis; later faults do not create an
unbounded recovery-command queue. Unexpected permanent-worker exit, panic,
closed command channel, or invalid forward command is a typed ownership or
fatal fault, not an ordinary DAG discontinuity.

`Start`, `Begin*`, `Catchup`, and `Live` are exact-once, state-specific
commands. Duplicate or invalid-state delivery is Fatal. `PpBoundarySealed` is
an exact-once, state-specific owner-directed event; a duplicate or
invalid-state milestone is likewise Fatal.
`Live` is exact-once separately for each processor; their sends need not be
simultaneous. VspcProcessor receives it at ordinary eligibility and
BlockProcessor only after block coverage succeeds. Enqueue is not completion.
Only `Deactivate` (formerly `Quiesce`) and `Shutdown` need completed-barrier
acknowledgements. `Deactivate` is idempotent to Idle. `Shutdown` is
terminal/idempotent from every state, dominates an in-progress Deactivate, and
acknowledges after full shutdown.
Unexpected command-channel closure is fatal while the worker is meant to live.
A dropped Deactivate/Shutdown acknowledgement receiver does not cancel the
transition; the worker completes its barrier.

Supervisor acquires usable RPC and DB capabilities concurrently without
blocking its event loop. Before `Start`, it checks that both services are
still Ready and publish the **same acquired** RPC and DB `Arc` generations,
ResyncEngine is Idle, and `desired_recovery` still equals the captured
requirement. **No PP/reconciliation fence belongs in Supervisor.** Node PP,
DB sink, and mode preparation belong to ResyncEngine. Earlier proposals that
moved them to Supervisor were rejected.

## 4. NodeService and validated RPC — settled

`NodeService` is a permanent autonomous lifecycle worker: connect, validate,
monitor IBD/connection, publish a usable connection generation, reconnect when
needed. `ValidatedRpcClient` is an `Arc`-shared capability bound to exactly
one physical gRPC connection; no automatic gRPC reconnect underneath it.

```rust
struct KgiConsensusParams {
    bps: u64,
    mergeset_size_limit: u64,
    anticone_finalization_depth: u64,
}
struct ValidatedNodeInfo {
    network_id: NetworkId,
    server_version: String,
    rpc_api_version: Option<u16>,
    rpc_api_revision: Option<u16>,
    consensus: KgiConsensusParams,
}

enum NodeServiceState {
    Connecting,
    Ready(Arc<ValidatedRpcClient>),
    Unavailable(NodeUnavailableReason),
    Rejected(NodeRejection),
    Stopped,
}
```

Transient connection, transport, and validation-RPC failures enter
`Unavailable` and retry indefinitely. Use nominal reconnect delays
`1s, 2s, 4s, 8s, 16s, 30s`, capped at `30s`, with equal jitter from 50%
through 100% of each nominal delay. The wait is shutdown-cancellable. Reset
the sequence only after the service has remained continuously Ready for
`60s`; merely opening a connection does not reset it. Network mismatch,
unsupported network suffix, incompatible RPC API, or missing required
notification capabilities enters terminal `Rejected` and is not retried
without changed configuration or process restart.

Copy only KGI-used consensus properties, not rusty-kaspa's entire `Params`.
After exact `NetworkId` validation, populate all three values from the pinned
rusty-kaspa `Params` selected by that network ID: `bps()`,
`mergeset_size_limit()`, and `anticone_finalization_depth()`. KGI must not
reconstruct the merge-set limit from BPS independently. Reject an unsupported
network type/suffix before constructing `Params`.
Validation checks exact CLI network type/suffix, RPC API compatibility,
`handle_stop_notify() == true`, and `handle_message_id() == true`. These
notification capabilities are mandatory; legacy Go kaspad is unsupported.
Wait for node to leave IBD before publishing a usable handle. The service's
`wait_until_usable()` waits through transient Connecting/Unavailable states,
but reports permanent Rejected/Stopped/closed. `NodeServiceState` and status
outlive individual validated client generations.

`NotificationRouter` implements `Notify`, owns the bounded BlockAdded and
VSPC senders, and has `Disabled | Enabled | Retired` states. Disabled drops
incoming notifications immediately; Retired never routes. Enabled routes
nonblocking; a full destination channel loses continuity, disables both
routes, and reports recovery. Router-disabled filtering and processor-local
notification gates are complementary. Before an Enabled router attempts its
bounded VSPC send, NodeService classifies a raw VirtualChainChanged
notification with empty `added`. If `removed` is also empty, discard the valid
upstream no-op without consuming capacity, earning overlap credit, altering
the committed sink, or requesting recovery. If `removed` is nonempty, do not
enqueue it: disable routing and report `Require(Resync)` because the
notification stream violated the selected-sink monotonicity invariant.

An Enabled `BlockAdded` without `RpcBlock.verbose_data` lacks the selected
parent and blue/red merge sets required by `BlockMaterialization` and reports
`Require(Resync)`.

The validated client's private mutex owns subscription state. Enabling both
BlockAdded and VirtualChainChanged is one logical all-or-nothing operation;
after both processors receive Catchup, keep the router Disabled while
starting both remote subscriptions. Enable local routing and publish the
client's subscription state as Enabled only after **both** starts succeed.
Callbacks arriving while Disabled during activation are intentionally
dropped, earn no overlap credit, and do not themselves request recovery.
Synthetic GetBlocks/VSPC production continues until normal Catchup overlap
establishes ordinary Live eligibility. The fixed body-tip coverage gate in
section 11 then accounts for activation-time BlockAdded drops before Live;
there is no separate callback replay. If either start fails, stop any started
subscription and retire the client when rollback is uncertain.
On disabling,
stop router delivery immediately, then `stop_notify` both remotely. Partial
subscription/unsubscription failure makes the connection's subscription state
uncertain and retires that handle. The validated connection, not NodeService,
owns its subscription lifetime. In a short Live IBD episode, connection loss
or violated stream invariants already causes recovery; a separate continuous
IBD mode is not a v2 requirement.

Only NodeService sees rusty-kaspa's raw VSPC notification; outside it:

```rust
struct VspcChange {
    removed: Arc<[BlockHash]>,
    added: Arc<[BlockHash]>,
}
```

`get_blocks(low_hash, include_blocks=true)` is normalized by the node layer:
raw hashes and blocks have equal lengths, first pair is the inclusive
`low_hash`, every hash matches its block, and hashes are unique. Strip that
first pair and return `Vec<SharedNodeBlock>`, without a redundant parallel
hash vector. It may return zero normalized blocks, and should not be treated
as a fixed full-page size. Use full blocks directly. Hash-only GetBlocks plus
one GetBlock per hash has no accepted local-node benefit. DependencyResolver
uses `GetBlock` for individual missing dependencies without transactions.

## 5. StorageService lifecycle and DB bootstrap — settled

`StorageService` mirrors NodeService: permanent connect/validate/reconnect
worker publishing `Arc<ValidatedDbClient>`, with a symmetric
`wait_until_usable()` contract. `ValidatedDbClient` represents one validated
DB connection/pool generation and owns its caches. A `ProcessingSession`
receives exactly one RPC generation and one DB generation; neither is rebound
mid-run.

```rust
struct ProcessingSession {
    rpc: Arc<ValidatedRpcClient>,
    db: Arc<ValidatedDbClient>,
}
```

A connection-level DB failure ends the session but does not retroactively
invalidate independent in-flight operations: actual committed writes remain
successes, definite rollbacks fail, ambiguous commit outcomes remain
ambiguous and are never transparently retried. All persistent mutations are
transactional. Cache publication follows commit; replacement generations
start with fresh caches. No extra DB generation number, handle revocation,
cache invalidation epoch, or global operation-completion barrier is needed.
The same validated DB/RPC `Arc`s are passed all the way to child workers and
released on Deactivate/Shutdown before the engine reports completion.

Storage connection and validation retries use the same independent nominal
`1s, 2s, 4s, 8s, 16s, 30s` sequence, `30s` cap, 50%-to-100% equal jitter,
shutdown cancellation, and `60s` continuously-Ready reset rule as
NodeService. Attempts are unbounded for transient availability failures.
Network binding mismatch and unsupported, newer, v1, partial, or unknown
schema states enter terminal `Rejected` rather than retrying.

Within one processing semantic transaction, only PostgreSQL SQLSTATE `40001`
(serialization failure) and `40P01` (deadlock detected) authorize a local
retry. Retry the **complete transaction** at most three times, after nominal
delays `10ms`, `50ms`, and `250ms`, each with equal jitter from 50% through
100%. Other definite failures are returned immediately. Connection loss
during commit is ambiguous and is never retried locally. Exhausting the three
transaction retries yields typed `Persistence(RetryExhausted)`: during an
active recovery it aborts the whole attempt with `Retry`; in Live it requests
`Require(Resync)`. Cache publication still occurs only after a definite
commit.

Startup distinguishes Uninitialized (no recognized KGI schema/binding),
Empty (valid network-bound v2 schema with no processing data), Initialized
(coherent PP, score, and materialized sink), and inconsistent or unsupported
layouts. `--initialize-db` is idempotent and safe in unattended service
configuration: initialize only Uninitialized, open a compatible existing DB
without erasing it, and never rebind its network. Without the flag, first
initialization requires interactive confirmation; noninteractive startup
fails with an actionable confirmation error. An existing network mismatch,
partial/unknown schema, newer schema, or v1 schema is rejected. A
structurally valid schema with inconsistent processing contents is usable
for Rebuild, not Resync; it is not misclassified as Empty.

StorageService holds a dedicated PostgreSQL session advisory lock before
initialization, migration, or validation and throughout its validated
lifetime. It rechecks state under that lock before any first initialization;
losing the lock connection retires the `ValidatedDbClient` and active
processing session. Supported older v2 schemas migrate forward through
ordered transactional migrations before a client is published. Automatic
down, online, or in-place v1→v2 migrations are forbidden.

`--clear-db` means processing-data Rebuild within the compatible network,
not network reinitialization. A persistent destructive
`--reinitialize-db --yes` startup flag is forbidden; a separate explicit
administrative reset remains deferred.

The correctness metadata, called **node metadata**, contains only
`network_id` and `db_pp_blue_score`. DB PP is located by `(level=1, slot=0)`,
not assumed to have ID 1 or minimum ID. API status/info exposes the
**currently validated** `ValidatedNodeInfo.server_version` to Web. Persisting
a last-known server version is not required for v2; observational node
information never determines recovery or network validation.

## 6. Retained persistence model and cache — settled

Identity and materiality are separate:

```text
block_identifiers(hash UNIQUE) -> CompactId
blocks(id)                   -> materialized graph/consensus data
```

Ordinary missing orphan hashes remain **only in memory**. Persistent
identity-only rows are created solely for hashes classified outside the
retained PP boundary, and are never promoted to `blocks`. Attempting to
materialize one later is an invariant violation. A row's existence alone is
not proof of correctness:

> `BoundaryMaterialized(b)` implies that b's retained DAG past is fully
> materialized according to PP-boundary semantics.

`BlockProcessor` enforces that invariant; `CompactId` existence does not.
PP bootstrap also interns synthetic ORIGIN as a permanent outside-boundary
identity when ORIGIN is the PP's selected parent. This includes Genesis and
any upstream PP carrying that selected parent; no nullable
`blocks.selected_parent_id` exception is introduced.

```rust
enum BlockPresence {
    Absent,
    BoundaryIdentity { id: CompactId },
    Materialized { id: CompactId, coordinate: BlockCoordinate },
}
struct CachedIdentity { id: CompactId, materialized: bool }
```

The conceptual SQL schema (column SQL types/migrations remain implementation
choices) is:

```sql
block_identifiers(
    id BIGINT PRIMARY KEY, hash BYTEA UNIQUE NOT NULL
        CHECK (octet_length(hash) = 32)
);
blocks(
    id BIGINT PRIMARY KEY REFERENCES block_identifiers(id),
    timestamp BIGINT NOT NULL, daa_score BIGINT NOT NULL,
    level BIGINT NOT NULL CHECK (level > 0),
    slot BIGINT NOT NULL CHECK (slot >= 0),
    selected_parent_id BIGINT NOT NULL REFERENCES block_identifiers(id),
    color ..., is_in_vspc BOOLEAN NOT NULL,
    blue_merge_set BIGINT[] NOT NULL, red_merge_set BIGINT[] NOT NULL,
    UNIQUE (level, slot)
);
levels(
    level BIGINT PRIMARY KEY CHECK (level > 0),
    size BIGINT NOT NULL CHECK (size > 0),
    daa_score BIGINT NOT NULL DEFAULT 9223372036854775807
);
parents(
    child_id BIGINT NOT NULL, parent_id BIGINT NOT NULL,
    child_level BIGINT NOT NULL, child_slot BIGINT NOT NULL,
    parent_level BIGINT NOT NULL, parent_slot BIGINT NOT NULL,
    PRIMARY KEY (child_id, parent_id),
    CHECK (parent_level > 0 OR parent_slot = 0)
);
```

`parents.child_id/parent_id` intentionally are **not** foreign keys. The
transaction validates them; rows embed both endpoint coordinates. An
outside-boundary parent uses `(0,0)` and is not drawn as a regular edge.
`levels.size` is the count of allocated slots at that level, not a horizontal
width. `levels.daa_score = i64::MAX` means no VSPC block at that level; real
DAA query values must remain below the sentinel. At most one VSPC block can
occupy a level. VSPC-empty levels are nevertheless possible after reorgs.

Storage caches (Moka is a candidate): hash→`CachedIdentity`, ID→coordinate,
ID→merge sets. Never cache negative identity results, mutable color, or VSPC
membership. Cold identity batches may left-join `blocks` to obtain the
materialized bit. Publish cache entries only after the corresponding commit.

Suggested internal storage concurrency uses separate sequential
materialization and VSPC mutation lanes, with transactions able to overlap;
Rebuild gets exclusive mutation access after processor Deactivate. Exact
mutex/`RwLock` arrangement remains implementation detail.

## 7. Block materialization and PP boundary — settled

```rust
struct BlockMaterialization {
    hash: BlockHash,
    selected_parent: BlockHash,
    direct_parents: Vec<BlockHash>,
    blue_merge_set: Vec<BlockHash>,
    red_merge_set: Vec<BlockHash>,
    timestamp: Timestamp,
    daa_score: u64,
    // other immutable KGI-used RPC fields, if required
}
enum ReferencePolicy { AllowBoundaryIdentities, RequireMaterialized }
struct MaterializeBlockOutcome {
    id: CompactId,
    coordinate: BlockCoordinate,
    inserted: bool,
}
```

`BlockMaterialization` is hash/consensus-level input; it contains no DB ID,
level, or slot. `ValidatedDbClient` owns transactional ID resolution,
coordinates, color initialization, and persistence. KGI takes only level-zero
direct parents from `RpcBlock.header.parents_by_level`, not higher parent
levels. For **every** materialization, intern hashes in this order:

```text
1 red merge-set hashes
2 blue merge-set hashes
3 direct-parent hashes
4 selected-parent hash
5 the block's own hash
```

Deduplicate first occurrences within that sequence. Validate unique parents,
selected parent among direct parents for **ordinary non-Genesis
materialization**, no contradictory self-reference, and
boundary materiality. A previously materialized own hash is a dedup outcome
returning its ID; own hash already classified as a permanent boundary
identity is an invariant violation. A new row starts Gray and outside VSPC.
The PP bootstrap path handles ORIGIN separately: it may set the non-null
selected-parent ID to ORIGIN even though ORIGIN is not an actual direct
parent. Genesis has zero actual direct parents, and this bootstrap exception
does not make ordinary `PersistedBlock.selected_parent` optional.

Strict policy requires all references materialized and creates no new
boundary identities. PreSeal policy may intern missing references as permanent
outside-boundary identities, but materializes the incoming block itself.
Ordinary unresolved orphans are never stored as identity-only rows. The
coordinate rule is:

```text
no materialized direct parent:
    level = 1; slot = next allocated slot at level 1
one or more materialized direct parents:
    level = max(materialized-parent.level) + 1
    slot = next allocated slot at that level
```

PP has slot zero at level 1. Retained PP-anticone roots (zero materialized
parents) get level 1 slots 1+. Other retained PP-anticone blocks can have
materialized anticone parents and use the normal parent-derived level rule. The term
“PP-anticone root” applies only to the first category; the observed retained
anticone comprises both. It is complete enough for KGI visualization, though
not claimed to be every mathematical anticone block. There are no placeholder
`blocks` rows and no promotion mechanism. Allocation is atomic, e.g.:

```sql
INSERT INTO levels(level, size, daa_score) VALUES ($1, 1, $no_vspc)
ON CONFLICT(level) DO UPDATE SET size = levels.size + 1
RETURNING size - 1;
```

`PreSeal` is the interval after a Rebuild PP is committed but before the
accepted BlueScore approximation seals the boundary:

```text
boundary_seal_blue_score =
    db_pp_blue_score + anticone_finalization_depth
```

PreSeal blocks are materialized in consensus-topological order under
`AllowBoundaryIdentities`, even with missing out-of-boundary parents/merge-set
identities. The retained portion of PP anticone precedes PP-future blocks
that merge it. The **first** block whose blue score is at/above the threshold
uses strict policy, not permissive policy. Only its definite successful commit
changes local boundary state to PostSeal and emits `PpBoundarySealed` upward to
ResyncEngine. ResyncEngine sends ApiService the PostSeal publication trigger
and propagates the milestone to Supervisor; neither owner sends it back as a
BlockProcessor command.
Rebuild must reach that definitely committed seal before Catchup; a Catchup
trigger while still PreSeal fails recovery. Resync starts PostSeal only after
reconciliation. Thereafter all cycles are strict. Before Catchup, a missing
dependency under strict policy fails the resync rather than becoming an
orphan. Catchup/Live
allow ordinary in-memory orphans.

```rust
struct PersistedBlock {
    point: VspcPoint,
    selected_parent: BlockHash,
}
```

On successful insert **or dedup**, BlockProcessor has the ID and publishes
`PersistedBlock` asynchronously to VspcProcessor and OrphanManager. The
normal `PersistedBlock` path represents non-Genesis blocks with a mandatory
selected parent. Genesis is handled by special bootstrap/reset logic; no
`VspcChange` added/removed member is Genesis, though a derived source can be.

## 8. BlockProcessor, orphan topology, dependency resolution — settled

One BlockProcessor event loop awaits inputs in strict priority:

```text
Command > Intern/resolved block > Notification block > Synthetic block
```

Use explicit higher-priority polling/draining around lower-priority work;
`tokio::select! { biased; ... }` alone does not provide the complete desired
priority contract under continually ready inputs. Commands include
`BeginRebuild`, `BeginResync`, `Catchup`, `Live`, `Deactivate`, `Shutdown`.
Begin resets all local state, overlap map/flag,
gates, orphan state, and descendants. It has no acknowledgement. The local
notification gate closes at Begin and opens on Catchup. Continue polling
notifications while closed and discard them immediately; do not accumulate
old notifications behind the gate.

A `BlockAdded` without verbose data cannot be materialized and requires Resync.

The first block filter checks processor phase and its source gate. Then query
storage for materiality. Already materialized blocks dedup, still yielding
their `PersistedBlock` identity to downstream consumers. For new blocks,
enforce the current boundary/strict policy and commit transactionally.
Failures follow phase policy: PreSeal boundary absences are accepted only as
outside-boundary identities, strict pre-Catchup missing dependency requires
Resync, and Catchup/Live blocks with unresolved ordinary dependencies become
in-memory orphans.

`OrphanManager` is an asynchronous child worker with separate prioritized
unbounded **Command** and bounded **Message** inputs. It owns orphan objects,
missing-dependency topology/frontier, reverse hash→waiting-orphans maps, and
`resolution_pending: HashSet<BlockHash>`. `BlockPersisted` resolves all
affected dependency edges; every newly ready orphan is removed from orphan
storage and returned through BlockProcessor's Intern lane. No waiter lives in
the committed-block index. Deduplicated hashes are harmless. On Begin/Deactivate
clear/cancel run-local state; Deactivate acknowledges after descendants stop.
After a successful resolver RPC, keep its hash in `resolution_pending` until
`AddOrphan` or `BlockPersisted` accounts for the returned block. RPC
completion alone does not close the logical request; doing so would create a
gap before BlockProcessor handles the result.

Dependency request selection uses only orphan topology, not DAA score or age.
As a rule of thumb, when occupancy reaches roughly 1/4–1/3 of capacity,
request hashes at the frontier to maximize release. Exact threshold/capacity
are implementation choices. An isolated orphan below threshold is acceptable:
silent notification loss is not a normal assumption; connection loss or full
notification channel causes recovery. No independent age fallback is required.

`DependencyResolver` is owned for lifecycle by BlockProcessor but driven by
OrphanManager. It has separate command/work channels, the session's exact
`Arc<ValidatedRpcClient>`, bounded concurrent GetBlock tasks, and task
cancellation. OrphanManager sends Resolve and `Cancel(hash)` for naturally
arrived blocks; it owns the pending set and avoids requery. Resolver results
return on BlockProcessor's Intern lane, not the notification lane. No DB
transaction is involved in GetBlock. Deactivation cancels/joins tasks and
releases RPC/DB session clones before acknowledging. There is no separate
`Satisfied(hash)` protocol. For OrphanManager→Resolver bounded message sends:
full→Resync, closed/unavailable→session fault, teardown cancellation→expected.
The resolver validates that GetBlock returned the requested hash. A
resolver-confirmed unavailable dependency requests `Require(Rebuild)`:
the retained DB can no longer be trusted against node state. An RPC or
connection failure follows the validated-client/session failure path and
does not itself prove unavailability. While deactivating, BlockProcessor
continues draining/discarding child results until child tasks have joined;
otherwise a full bounded result channel could deadlock the barrier.

## 9. VSPC changes, readiness, history, and atomic coloring — settled

`VspcChange` removes the old chain suffix in reverse order (old sink first)
and adds the new suffix in forward order (new sink last), excluding the common
ancestor. Source and destination hashes derive as:

```text
source = removed.first() if removed nonempty
       = selected_parent(added.first()) otherwise
destination = added.last()
```

Every **admitted nonempty** change must have an `added` member. A
removed-only change is impossible at the pinned upstream revision: it would
require the new selected sink to be a strict selected-parent ancestor of the
previous sink even though virtual sink selection cannot regress behind its
still-valid previous sink. Do not derive a fallback destination from
`removed`. NodeService rejects that shape with `Require(Resync)` when it
arrives as a notification. The synthetic pump aborts the complete recovery
attempt with the bounded typed `Retry` policy in section 3; it neither
dispatches the change nor advances its cursor.

Pinned upstream inspection also shows that side-block virtual processing can
emit a raw notification with both vectors empty when the selected-chain sink
does not move. NodeService discards that no-op before constructing or sending
`VspcChange`; VspcProcessor never receives it. An empty VSPC V2 **page**
remains distinct synchronization information, not a change. VSPC
added/removed never contain Genesis. No redundant
`PendingVspcChange` wrapper is needed: the pending structure holds
`VspcChange` plus indexing metadata.

```rust
struct ReadyVspcChange {
    source: VspcPoint,
    destination: VspcPoint, // includes ConsensusOrder
    removed: Arc<[CompactId]>,
    added: Arc<[CompactId]>,
}
```

There is no `ReadyAddedBlock`: the DB transaction loads merge sets. A ready
change carries only the IDs/order needed for readiness and sequencing, not
all storage-execution detail. `CHAIN_READY` means source equals committed
sink. `BLOCK_READY` means destination is `BoundaryMaterialized`. Both are
required even during PreSeal. Since retained PP-anticone materializes before
its PP-future merges, missing merge-set identities can be ignored for color;
a directly added/removed chain block that is not materialized is an invariant
violation requiring `Require(Rebuild)`. This direct-chain fault is distinct
from an identity-only merge-set member outside the retained PP boundary.
The same committed source/destination chains are monotonic; source
of the next committed change equals the last committed destination. Arrival
order of competing notifications need not be monotonic.

Resolution must work both event-before-block and block-before-event. Keep an
ordered synthetic FIFO, raw unresolved notifications indexed by
`added.last()` destination hash, and resolved notification candidates
ordered by destination `ConsensusOrder`. These structures share one
bounded pending capacity. Pending ID→change and missing-hash→waiting-ID
indexes support dependency resolution; recent hash→`PersistedBlock` and
`ConsensusOrder→hash` support history/pruning. Resolve **both** source and
destination before a notification is actionable. An unresolved old
notification cannot head-block a later actionable one or earn overlap credit
merely because its raw destination hash is known. For `removed=[]`, source
is selected parent of first added and all member IDs resolve from history;
the strict-`<` history rule retains the source for an actionable added-only
change.

For an actionable reorg, `ValidatedDbClient::resolve_materialized_ids`
receives `removed` followed by `added` in one ordered batch. It returns an
ID for each input position (including repeated hashes), uses cache hits and
at most one SQL read, and performs no writes, interning, or identity
promotion. Missing and identity-only chain members are distinct typed
errors, both requiring Rebuild. A crossing reorg normalized to added-only
uses history and does not call this read API. Endpoint `VspcPoint` order
comes from materialization history; the DB batch resolves member IDs, not
consensus order or merge sets.

During Catchup classify a resolved notification against committed synthetic
sink `C` in this order:

1. Let `D = added.last()`. If `D.order <= C.order`, discard it under the
   Catchup lower-bound/overlap rules. Eligible accepted history may give
   overlap credit. Do not construct an empty normalized change when `D == C`.
2. If `D.order > C.order` and `C.hash` occurs in `added`, normalize by
   dropping `removed` and the `added` prefix through `C`. The resulting
   added-only suffix is necessarily nonempty and has source `C`.
3. Otherwise derive and resolve the original source. If it equals `C`, the
   original change is directly actionable.
4. Otherwise retain it pending and continue scanning later candidates; it
   must not head-block an actionable notification.

A consensus-order comparison, a later destination, or the sink's occurrence
in `removed` is insufficient to prove crossing. Resolve both endpoints of the
resulting actionable change before readiness. Distinct incompatible
candidates request Resync.

The materialization-history rule is phase-specific:

```text
Before Catchup: prune history entries with order < committed VSPC sink.
Catchup:       do NOT prune on synthetic/notification commits.
Catchup→Live:  prune entries with order < committed VSPC sink.
Live:          prune entries with order < sink after each successful commit.
```

Keep the sink entry (`<`, not `<=`). Do **not** delete buffered notifications
merely because their destination is below the sink without applying the
phase-specific filtering/overlap logic. A resolved notification proved
between the Catchup lower bound and committed synthetic sink may be
discarded with overlap credit only when its history proves that meeting;
older latecomers and unresolved raw destinations receive no credit.
In Live, a rare network-delayed notification that
cannot resolve after history pruning can remain non-actionable in the bounded
pending structure; it must not block a later actionable crossing transition.
If latecomers saturate the bounded structure, request Resync. A duplicate
transition from the same notification source is an invariant violation and
requests Resync, not silent idempotent discard.

Storage's `apply_vspc_change` validates source against current committed
materialized VSPC sink, materiality of all added/removed chain members, and
no duplicate/intersecting members. It atomically removes old VSPC membership
and resets relevant colors to Gray; adds chain membership; for each added
member, applies materialized blue merge-set colors Blue then materialized red
merge-set colors Red (red wins overlap). Identity-only merge-set members are
ignored in both policies. It updates `levels.daa_score` to the final VSPC
occupancy/sentinel as needed; API does **not** require a returned list of
changed levels. The transaction returns destination `VspcPoint` naturally,
avoiding caller-side clone. There is no dedicated persisted VSPC-sink table:
derive sink from maximum-ID materialized `is_in_vspc=true` block.

## 10. ResyncEngine preparation and common pump — settled

```rust
struct PreparedSync {
    rpc: Arc<ValidatedRpcClient>,
    db: Arc<ValidatedDbClient>,
    anchor: MaterializedSyncAnchor,
    boundary_seal_blue_score: u64,
}

enum EngineCommand {
    Start {
        mode: RecoveryMode,
        rpc: Arc<ValidatedRpcClient>,
        db: Arc<ValidatedDbClient>,
    },
    Deactivate,
    Shutdown,
}
```

No `ProcessingResources` wrapper is needed; `PreparedSync` directly holds the
two resources. The exact same validated `Arc`s propagate through the run,
including DependencyResolver. Resync and Rebuild prepare this common struct,
then use one GetBlocks/VSPC synchronization pump. Their essential difference
is PreSeal storage policy in a new Rebuild DB; Resync starts PostSeal/strict.

**Resync preparation:** read DB PP from `(1,0)`, `db_pp_blue_score` metadata,
and the committed materialized VSPC sink's ID, hash, and stored DAA score. A
genuinely Empty network-bound DB has no PP/score/sink and therefore reports
`Require(Rebuild)` to Supervisor; it starts a distinct Rebuild run, never an
internal clear-and-continue. A structurally valid but inconsistent processing
DB likewise requires Rebuild and is not treated as Empty; invalid schemas were
already rejected by StorageService.

For an Initialized DB, ResyncEngine constructs the sink anchor through the
run's exact `Arc<ValidatedRpcClient>`:

1. call `GetBlock(sink_hash, include_transactions = false)`;
2. require `response.header.hash == sink_hash`;
3. require `response.header.daa_score == stored_sink_daa_score`;
4. combine the stored ID and hash with `response.header.blue_work` and
   `response.header.blue_score` to construct `MaterializedSyncAnchor`.

A header-only node block is sufficient: anchor construction needs header and
GhostDAG data, not transactions. At the pinned rusty-kaspa revision, a
successful GetBlock performs the same GhostDAG-data lookup that validates a
GetBlocks `low_hash`; it therefore also establishes that the node recognizes
the committed DB sink as the pump anchor. The current **node PP** must be
BoundaryMaterialized in DB. Require:

```text
S.blue_score >= db_pp_blue_score + anticone_finalization_depth
```

`S` is the committed **DB** sink, not node PP. A missing or structurally
inconsistent stored sink, a definitive node response that the sink is absent
or invalid, or a stored/returned DAA-score mismatch requests Rebuild via
Supervisor. A transport failure, cancellation, connection loss, or validated
client loss is a session fault/retry and does not establish a Rebuild need. A
GetBlock response for a hash other than the requested sink is a malformed RPC
response and a protocol/session fault, not evidence against the DB. There is
no Auto or internal fall-through to DB clear. ResyncEngine performs these
checks; Supervisor must not inspect them.

**Rebuild preparation:** the sole processing-data clearing API is:

```rust
async fn rebuild_from_pruning_point(
    pp: SharedNodeBlock,
) -> Result<MaterializedSyncAnchor, DbError>;
```

The PP argument is mandatory. The one transaction clears processing data,
restarts identity allocation, interns PP boundary references, materializes
PP `(1,0)`, marks it VSPC, seeds `levels`, persists `db_pp_blue_score`, and
commits before returning anchor. Configuration/schema/network identity
survive. Cache reset/seed is published after commit. This is not a general
“clear DB” primitive callable without a PP.
If the PP selected parent is synthetic ORIGIN, the transaction interns
ORIGIN as a permanent outside-boundary identity and uses its non-null ID.
Genesis's actual direct-parent list remains empty.

For Rebuild, the engine instructs ApiService with an acknowledged
database-rebuild `Reset` **before** starting this DB-clear transaction; see
§15 for the API barrier. For ordinary Resync, successful reconciliation is
followed by an acknowledged session-replacement `Reset` and a PostSeal
publication trigger before processor Begin. A failed read-only reconciliation
requests Rebuild without resetting ApiService. Before each new processor Begin,
the engine disables/unsubscribes both notifications. Then it sends Begin to
both processors, without Begin acknowledgements.
Their local gates drop late notifications until Catchup. Before enabling
subscriptions again, send both Catchup messages. Keep the router Disabled
during both remote start calls; activation callbacks are dropped and do not
count for overlap. Enable routing only after both starts succeed. Command
priority ensures processor gates open before newly routed notifications are
processed.

The pump manages one normalized GetBlocks page and one pending VSPC V2 page.
Call `GetVirtualChainFromBlockV2` with
`min_confirmation_count = None` and
`data_verbosity_level = Some(RpcDataVerbosityLevel::None)`. Omitted
verbosity defaults to Full; positive confirmation counts can remove the
head from `added` and break the progress cursor. This exact combination was
verified against rusty-kaspa master `c338d495`: explicit `None` verbosity
retains the minimal acceptance-data envelope, and a nonempty response keeps
an advancing `added.last()` cursor. The merge-set acceptance-data budget may
shorten `added` to a complete prefix. Preserve this behavior with a pinned
regression fixture. A response with empty `added` and nonempty `removed` is a
typed `RemovedOnlySyntheticVspc` fault: do not dispatch it or advance the
cursor, and abort the whole attempt under the section 3 `Retry` policy.
Conceptually:

```text
request VSPC V2 from current low_hash (gapless incremental chain)
  ├─ empty page: maybe trigger Catchup; retry at bps-derived interval
  └─ nonempty: derive its destination
dispatch GetBlocks blocks until destination was SENT to BlockProcessor
pause a returned GetBlocks page suffix when necessary
send synthetic VspcChange to VspcProcessor
request next VSPC page; resume the block suffix
```

“Sent” means accepted into BlockProcessor's channel, not materialized/acked.
Neither engine nor VSPC RPC waits on processor commits; failures request
their typed recovery disposition or eventually saturate unprocessable VSPC
state.
Synthetic VSPC changes are ordered/gapless because each incremental call uses
the preceding destination. Never invent an extra journal or notification
dispatcher in the engine.

This coordinated mode ends when ordinary Live eligibility is first observed
at a fully dispatched GetBlocks-page boundary. Section 11 defines a bounded
coverage phase after that point. ResyncEngine stops issuing VSPC V2 calls and
sending synthetic `VspcChange` messages, stops/joins that producer, and sends
VspcProcessor its existing Live command. VspcProcessor abandons synthetic
input for the rest of the session and makes notifications authoritative while
ResyncEngine advances only a separate block scan. The Catchup-only set of
successfully sent synthetic block hashes is coverage accounting, not a general
notification journal.

## 11. Catchup, overlap, Live, and late transport messages — settled

At the start of the GetBlocks scan, capture `catchup_sink = GetSink()` and the
DAA score from that exact block's immutable header. This is a rolling Catchup
marker, not a stable snapshot of the virtual state. The synthetic VSPC pump
tracks the marker through its ordered, gapless responses:

```text
Unknown -- marker equals the synthetic cursor or occurs in added --> Present
Present -- marker occurs in a later removed --> Removed
```

`Present` means the marker is the current synthetic cursor or has occurred in
a synthetic `added` path, and no later pump response has removed it. Cursor
equality covers an already synchronized starting point, which will not be
repeated in `added`. A marker occurring in `removed` is conclusive
invalidation because rusty-kaspa returns the complete removed suffix even
though it bounds `added`. Absence from `removed` while `Unknown` proves
nothing: the marker may have left the selected chain before the pump ever
admitted it.

Before dispatching a normalized GetBlocks page containing the current marker,
hold the whole page and refresh the sink with `GetSink()`. Load the header for
that exact returned hash and calculate the checked DAA-score difference from
the marker. Define:

```text
catchup_max_daa_gap = max(
    30 * network_bps,
    mergeset_size_limit + 1,
)
```

The page-size floor reflects the atomic transition granularity: the held
GetBlocks page is dispatched wholly under Catchup. On current parameters the
threshold is 181 at 1 BPS, 300 at 10 BPS, and 960 at 32 BPS. It remains below
the VSPC V2 added batch size of `10 * mergeset_size_limit`.

Enter Catchup before dispatching the held page only when the marker is
`Present`, the fresh score is not below the marker score, and the difference
is at most `catchup_max_daa_gap`. If the difference is larger, replace the
marker with the fresh sink, reset its pump state to `Unknown`, and remain in
Resync. If the replacement marker is already in the held page, re-evaluate it
before dispatch; otherwise continue the scan. A marker observed by GetBlocks
but not yet established by the VSPC pump remains reached and is reconsidered
at a later complete page boundary. A `Removed` marker or a decreasing score
cannot authorize Catchup; refresh the marker and continue Resync.

The pump continues through Catchup, so a reorg after the final comparison is
handled by a later synthetic VSPC change. The rolling marker is the primary
Catchup path. Preserve these independent fallbacks when it has not authorized
the transition:

```text
the normalized GetBlocks page's global maximum ConsensusOrder is not final
OR
the normalized GetBlocks page contains fewer than three blocks
OR
the VSPC V2 page is empty
```

For a stable below-sink view, the ordered core's `highest_reached` is its
final global maximum. A
nonempty appended sink anticone leaves that sink maximum before the final
block. With merge-set limit `L` and core budget `L + 1`, a below-sink
capacity stop has at least three normalized blocks; length `< 3` is therefore
a one-way sink-reaching proof. Evaluate either GetBlocks fallback on the
complete normalized page and enter Catchup before dispatching it. An empty
VSPC V2 page enters Catchup without advancing the VSPC cursor; retry from the
same cursor at the target block interval derived from network `bps`. A short
nonempty VSPC page is not a fallback.

The rolling marker is the normal transition path; these fallbacks cover an
exceptional failure to enter Catchup through it. Do not add a separate
mixed-virtual-view recovery protocol for GetBlocks. If an earlier omission
becomes material while processing is still strict before Catchup, the normal
strict missing-dependency fault requests `Require(Resync)` and the full
recovery cycle handles it.

ResyncEngine must have observed BlockProcessor's definitely committed
`PpBoundarySealed` event before the primary gate or any fallback enters
Catchup. Eligibility while still PreSeal fails that recovery attempt.

No notification epoch can be assigned reliably across unsubscribe/resubscribe
because old transport packets can arrive late. Begin resets each processor's
all local state and closes the gate. Catchup opens it with objective lower
bounds:

```rust
struct BlockCatchup {
    // Conceptual compact-ID lower bound from latest GetBlocks anchor/page.
    known_id_lower_bound: CompactId,
}
struct VspcCatchup {
    synthetic_sink_lower_bound: VspcPoint,
}
```

These sketches do not fix message enum syntax. Known BlockAdded below the
CompactId lower bound is discarded without overlap credit; unknown blocks
are not rejected on guessed order. A notification below sealed PP is
discarded/invalid. For a VSPC notification, a destination below the
synthetic-sink lower bound is a latecomer and discarded without overlap
credit. Once Catchup is entered, legitimate delayed block notifications
can harmlessly dedup, persist, or orphan; no timer grace/epoch is required.
Callbacks intentionally dropped during remote subscription activation
receive no overlap credit. The coordinated synthetic pump remains active
until the ordinary overlap checks pass. The bounded body-tip coverage phase
below, rather than an assumption about callback replay, establishes gapless
block admission before Live.

Each processor owns an `AtomicBool` overlap flag read by ResyncEngine. Begin
resets it, Catchup starts accounting. BlockProcessor tracks one
`HashMap<BlockHash, SourceBits>` with `SYNTHETIC=1`, `NOTIFICATION=2`. A hash
seen from both sources proves block overlap. One normalized GetBlocks response
has unique hashes, but hashes may repeat across successive responses because
the server deduplicates only within a response and can return the same sink
anticone again. ResyncEngine therefore owns an exact `catchup_sent` hash set
from Catchup entry through Live/Deactivate and inserts a hash only after the
synthetic block channel accepts it. It filters later synthetic repeats before
dispatch; a filtered repeat earns no overlap credit. BlockAdded within one
subscription is expected not to duplicate, and an unexpected duplicate from
that notification source remains an invariant fault. Engine examines the
block overlap flag only after a **fully dispatched GetBlocks page**; never
abandon an already-returned page suffix before that point.

While the coordinated Catchup pump supplies synthetic changes, VspcProcessor
commits that gapless stream in order. Notifications are consumed/resolved and
used for overlap, but do not overtake an available synthetic predecessor. Once
ordinary eligibility is reached, ResyncEngine stops/joins synthetic VSPC
production and sends the existing VspcProcessor Live command. That exact-once
component transition discards queued synthetic input and ignores that input
for the rest of the session; retained/new actionable notifications may then
commit. A temporary synthetic-queue gap before Live never authorizes a
notification commit. A notification transition can cross the synthetic sink;
it need not end at an exactly equal destination. A crossing is
demonstrable when the committed synthetic sink occurs in the notification
`added` sequence; discard `removed` and the prefix through that sink to
normalize an actionable suffix. A resolved notification between the Catchup
lower bound and committed sink can provide overlap credit only when its
history proves the meeting. Order comparisons and unresolved raw destinations
cannot. Do not count filtered older latecomers. A duplicate notification
transition is a Resync-worthy invariant breach.

At a fully dispatched GetBlocks-page boundary,

```text
PostSeal && block_overlap && vspc_overlap
```

establishes **ordinary Live eligibility**. It does not authorize
BlockProcessor Live or global `EnteredLive`; it authorizes VspcProcessor's
component-local Live transition and a bounded block-coverage phase.

ResyncEngine stops issuing VSPC V2 calls and sending new synthetic
`VspcChange` messages, stops/joins the VSPC producer, and successfully enqueues
VspcProcessor's existing Live command before starting coverage requests.
Command priority transitions VspcProcessor to notification-authoritative Live
and clears/discards remaining synthetic input for this session. This is not a
new processor phase, checkpoint, or barrier. Available block material lets its
committed sink advance; a notification change whose block material is not
ready remains pending under the ordinary readiness rules. This waiting occurs
before strict materiality resolution and does not weaken the direct Rebuild
fault when an actionable VSPC transition names a chain member confirmed
nonmaterialized.

After stopping synthetic VSPC production, capture one fixed body-tip set `T`
from `GetBlockDagInfo.tip_hashes`. Only that tip vector is the coverage
snapshot; other response fields are not an atomic combined snapshot. In one
batch determine `M`, the members of `T` already strictly materialized in the
database. This relies on the pinned rusty-kaspa ordering that a body commit,
including its body-tip-store update, completes before its BlockAdded
notification is emitted. Do not refresh `T`: body commits after its capture
are covered by the already-active reliable BlockAdded subscription.

Continue a **block-only** GetBlocks scan using its own existing cursor. Keep
the normal complete-page/suffix discipline and filter hashes already in
`catchup_sent`. There must be at least one additional coverage request.
Rate-limit additional request starts to one per target block interval:

```text
coverage_page_interval = 1 second / network_bps
```

If page dispatch already exceeds the interval, add no sleep. Let `L` be the
merge-set size limit and define:

```text
get_blocks_core_capacity = L + 1
coverage_page_cap =
    1 + ceil(catchup_max_daa_gap / get_blocks_core_capacity)
```

This gives caps of 2 pages at 1 BPS, 3 at 10 BPS, and 3 at 32 BPS with current
merge-set limits 180, 248, and 512. The cap counts additional successfully
returned, fully dispatched GetBlocks responses after ordinary eligibility; an
empty or fully filtered response still counts. It is an operational retry
budget, not a claimed DAA progress bound.

After each complete coverage page, Live admission requires:

```text
T ⊆ M ∪ catchup_sent
```

The invariant means every retained body tip present at the coverage snapshot
was already materialized or its block was successfully admitted to
BlockProcessor during Catchup. Strict processing makes missing ancestry
explicit as queued/orphan dependency work, and Live preserves that work.
Together with reliable BlockAdded delivery after the fixed snapshot, this is
the gapless block-admission guarantee; it does not assert that all admitted
blocks have committed before Live.

When the invariant holds, stop and join the block coverage producer, then
enqueue BlockProcessor's Live command. BlockProcessor retains valid
queued/orphan work. VspcProcessor is already Live and continues from its actual
committed sink; coverage does not establish or preserve a separate checkpoint.
Only after the earlier VspcProcessor Live enqueue and the final BlockProcessor
Live enqueue have both succeeded may the engine emit `EnteredLive` and send
ApiService the Live publication trigger; this does not certify empty worker
queues or completed previously queued work. If the
invariant is still false after the capped page, request `Require(Resync)` and
do not send BlockProcessor Live. Normal deactivation terminates
VspcProcessor's component-local Live run. Recovery derives its starting sink
from the database state committed by VspcProcessor at that time. Normal Live
invariants continue to detect later mistakes and require recovery.

If a short IBD occurs while already Live, no new continuous-IBD mode is
required in v2. A low-frequency Live VSPC consistency probe remains a v2.1
candidate.

## 12. Teardown and delivery/failure semantics — settled

On Deactivate: close routing gates/disable remote subscriptions; cancel/join
sync producers; clear engine buffers; send Deactivate to processors; await
their descendant barriers; release **both** RPC and DB session clones below
the engine; drop the `ProcessingSession`; report Deactivated/Idle. The
ValidatedRpcClient and ValidatedDbClient may still have service-owned Arcs;
the invariant is no old **processing-session** clone remains. Shutdown stops
engine/processors before NodeService then StorageService. A `Shutdown`
request supersedes a concurrent Deactivate.

Message delivery semantics depend on channel role. A full bounded Live
session-data channel means the ordered stream may have a hole and requires
Resync, even if DB commits remain coherent. Closed worker channel indicates
child liveness/ownership failure (session fault), not benign overload.
Cancellation because teardown is already in progress is expected. A failed
`PersistedBlock` delivery after successful DB commit cannot be ignored: the
receiver cannot distinguish “not yet seen” from “lost forever.” A new
session rederives authoritative DB state. Graph observer loss follows a
different rule: invalidate/reload API image without disrupting processing.

## 13. In-process API and graph observer feed — settled

KGI v2 includes an in-process `ApiService` and a complete bounded-by-level
`HeadGraphCache` (HGC), rather than directing each head request to expensive
PostgreSQL graph queries. This remains a valid foundation for future scale:
later deployments could separate multiple read-only API replicas from a
single writer/processor, but multiple full processing stacks and DB
replication are not required in v2.

Processors send `BlockCommitted`/`VspcCommitted` through **one ordered,
bounded graph-update channel**, after their respective DB commits. The
BlockProcessor sends a newly committed block's graph update before passing
its `PersistedBlock` to VspcProcessor. Thus a VSPC update cannot reach this
single API channel ahead of the blocks it causally depends on. The observer
channel is nonblocking from the processing viewpoint: failed/full delivery
sets an out-of-band invalid flag; ApiService stops publishing deltas and
reloads from DB. No processing recovery or producer sequence number is
needed for observer-only continuity. The invalid flag also catches loss of
the **last** update that no subsequent sequence number could expose.

Conceptual committed payloads (field names can change, semantic content
must not):

```rust
struct GraphParent {
    hash: BlockHash,
    coordinate: Option<BlockCoordinate>, // None at outside-PP boundary
    level_size: Option<u64>,              // needed for external endpoint
    is_selected: bool,
}
struct BlockCommitted {
    hash: BlockHash,
    coordinate: BlockCoordinate,
    timestamp: Timestamp,
    daa_score: u64,
    direct_parents: Arc<[GraphParent]>,
    blue_merge_set: Arc<[BlockHash]>,
    red_merge_set: Arc<[BlockHash]>,
}
struct VspcCommitted {
    source: BlockHash,
    destination: BlockHash,
    removed: Arc<[BlockHash]>,
    added: Arc<[BlockHash]>,
}
```

The parent payload includes both direct and selected-parent coordinates
without duplicating the selected parent. Updates for blocks outside current
HGC still need examination: a new block can increase `levels.size` at an
external parent endpoint used by an edge crossing the cache boundary. The
size of an external level may be seeded by an incoming child's parent data
and then updated monotonically when later blocks occupy it.

ApiService applies VSPC source/destination continuity:

```text
incoming.source == cache.committed_vspc_sink
```

If not, invalidate/reload HGC. From the removed/added vectors and cached
block metadata, ApiService independently updates cached VSPC membership,
colors, and level DAA scores, then publishes **one atomic graph revision**.
Processing/storage need not return a list of DAA-score changes or track them
for the API. Only actual final level-score changes matter: a remove/add pair
may temporarily change then restore a level's original score. An added
block's merge-set hash absent from complete HGC levels has no impact on
retained levels by definition; ignore it rather than invalidating cache.
Do not confuse this with a required chain block missing from cache when its
effect on a retained level cannot be determined; that case requires reload.

`MAX_CACHE_DEPTH = 1000` complete levels. Define a separate
`MAX_WINDOW_DEPTH <= MAX_CACHE_DEPTH`; its exact value remains to select.
No arbitrary maximum block count may truncate a retained level: **every**
block and relevant edge endpoint for each cached level is available. Every
windowed endpoint caps requested depth to `MAX_WINDOW_DEPTH` and reports
the effective range. An oversized `/graph/head` request cannot fall back to
DB; it is capped. A cache memory budget may make the whole image temporarily
unavailable, never partially populated. Process work retains resource
priority.

The v1 edge rule remains: emit **every materialized edge whose span
intersects the requested window**, including a parent outside the response.
At the head, every such edge has its child in HGC, while its parent can be
outside. Retain cached child→parent records, parent hash/coordinate, and
the external parent's level size. Do **not** require both endpoint blocks
inside the requested window, nor omit a crossing edge. PP-boundary sentinel
edges at level 0 are not normal visible materialized edges.

`CompactId` is private to storage/processing. Each HTTP graph response has
its own small numeric references and an included local ID→hash dictionary
covering **all** hashes it references, including off-window parent endpoints
and merge-set members. The Web graph/domain model identifies blocks by hash
only. These local IDs are not persistent across responses or instances;
coordinates may diverge across independently allocated DBs.
The public block projection preserves its **actual direct-parent list** even
when some parents are outside the response or PP boundary and have no
drawable edge. Web identifies a present Genesis by zero actual direct
parents, never by zero visible parent edges or by an ORIGIN marker.
This marker requires neither a persisted network Genesis hash nor a dedicated
Genesis-hash API endpoint.

## 14. API snapshot, revision, delta, SSE, and ETags — settled

ApiService begins buffering graph updates **before** a consistent DB snapshot
read. The snapshot includes complete retained levels/blocks, external edge
endpoint coordinates and level sizes, current colors/VSPC membership,
committed VSPC sink, and current DB data needed for DAA resolution. Replay
buffered block updates idempotently without overwriting snapshot colors;
skip VSPC prefix already represented by the snapshot, then require exact
source/sink continuity. On each new processing session, reload because the
previous session may have committed data without publishing its observer
update. Every reload creates a new **GraphEpoch**: this is an API publication
continuity epoch, not a DB, node, notification, or CompactId epoch. An old
coherent image can remain served as explicitly **stale** until a coherent
replacement is ready, but it has no active deltas.

ApiService has three externally meaningful publication states:

```text
Stale | Synchronizing | Live
```

Reset makes the old epoch Stale. The PostSeal trigger starts snapshot/replay
and publishes its coherent replacement as a new GraphEpoch in Synchronizing
state. Synchronizing is a valid current-DB image: head snapshots, deltas, and
SSE are available while processing catches up. The Live trigger changes that
same epoch to Live without another reload or epoch change. If Live arrives
while the replacement is still loading, remember the newer target and publish
the completed image directly as Live. A later Reset cancels any pending
publication and returns the API to Stale.

Each graph mutation and each active-epoch lifecycle-state change produces an
atomic revision. Reset retires its epoch and need not create an old-epoch
delta. A snapshot carries `(GraphEpoch, revision, publication_state)`. Deltas
describe a contiguous interval `(a,b)` within one epoch, are **independent of
requested window depth**, and compose sequentially:

```text
apply(Delta(a,b), image_at_a) = image_at_b
apply(Delta(b,c), image_at_b) = image_at_c
```

A lifecycle-only revision carries the publication-state update even when graph
data is unchanged.

Absolute set/upsert patches are preferable to fragile relative instructions.
Each delta response uses its own response-local hash dictionary. Retention is
bounded. Epoch mismatch, unavailable revision, stale API, or too-old cursor
requires a fresh snapshot, never a partial delta. Whether adjacent revisions
are encoded as individual records or a coalesced patch is implementation
choice as long as the composability contract holds.

SSE is only an ordered **cursor wakeup** `(epoch, revision)`, not the graph
data channel. A browser `EventSource` can receive a sequence on one
connection, but reconnection is not exactly-once. On connect the server
immediately emits the latest cursor; subsequent publications emit updated
cursors. Slow clients get coalesced cursor notifications and, if persistently
behind, are disconnected; they reconnect and use HTTP delta or snapshot.
The Web keeps one in-flight catch-up loop and coalesces desired cursors.

`representation_version` is the settled term for the graph payload schema.
An ETag for a head snapshot distinguishes epoch, revision, effective window,
negotiated response format, representation_version, and publication state;
`Cache-Control: no-cache` allows cheap revalidation/304. A fixed delta
interval `(epoch,from,to)` is immutable and cacheable. A “to current” query
must revalidate. SSE has no ETag. Historical DB windows have **no ETag in
v2**, because computing an authoritative validator would itself require DB
work. Exact graph wire format is intentionally not chosen yet: benchmark
JSON vs appropriate binary formats (CBOR, MessagePack, Protobuf, etc.) over
server construction/serialization, compression, transfer, browser decode,
and graph-model construction. SSE stays small text cursor events.

## 15. Reset and recovery-time API availability — settled

The existing reliable processing→ApiService control path carries conceptual
`Reset`, `PublishPostSeal`, and `PublishLive` controls; no new recovery
component is needed. Every prepared processing session sends exactly one
Reset. Common Reset
effects are:

- mark the previously published HGC image Stale while allowing that coherent
  old image to remain readable;
- stop old-epoch deltas;
- prevent pending observer updates from the previous processing session from
  entering the replacement epoch; and
- arm buffering for the new session before processor Begin.

Reset has a completed-effect acknowledgement. The acknowledgement establishes
those effects but does not mean that a replacement image has been published.
Ordinary graph-update loss semantics do not weaken this reliable control
barrier. The exact command representation remains an implementation detail.
PostSeal and Live are reliable, exact-once, state-specific controls, but they
are not processing barriers and have no publication-completion
acknowledgement.

Ordinary Resync performs read-only reconciliation first. Failure requests a
separate Rebuild without resetting ApiService. On success, ResyncEngine sends
the session-replacement Reset, awaits its acknowledgement, and sends the
PostSeal publication trigger before processor Begin. Because Resync does not
clear processing data, new and in-flight historical DB reads remain available.

For Rebuild, obtain the pruning point, send the database-rebuild Reset, and
await its acknowledgement before `rebuild_from_pruning_point`. This Reset has
the additional completed effect of closing new historical DB reads and
boundedly draining or cancelling existing ones. Historical window requests
during `RebuildingDatabase` and `PreSeal` fail cleanly with
`503 Service Unavailable` and a short `Retry-After`. Merely catching SQL errors
is insufficient: a query against a partly reconstructed DB can succeed but
return an incomplete graph. A read already in flight may return its old
coherent snapshot if it completes before the reset barrier; otherwise cancel
it and return 503. API reads cannot indefinitely delay processing.

For Rebuild, ResyncEngine sends the PostSeal publication trigger only after it
observes BlockProcessor's definitely committed `PpBoundarySealed` event. For
ordinary Resync, successful reconciliation already establishes PostSeal, so
the trigger follows Reset acknowledgement directly. PostSeal starts the
consistent snapshot plus buffered-update replay. Once coherent, ApiService
publishes a new GraphEpoch in Synchronizing state; this publication reopens
historical reads after Rebuild. Processing does not wait for it to complete.

When the global `EnteredLive` conditions hold, ResyncEngine sends the Live
publication trigger. ApiService publishes the state change atomically as a new
revision in the same GraphEpoch, so snapshot validators, deltas, and SSE
clients observe it without another reload. If PostSeal loading has not
finished, ApiService records the newer target and publishes the completed
image directly as Live.

If `TRUNCATE` is used inside the atomic rebuild, its transactional rollback
does **not** make it generally MVCC-safe for concurrent pre-existing
snapshots. Implementation must prove pre-reset reads return one old coherent
image or get canceled, never mixed old/new tables. See PostgreSQL's
[`TRUNCATE`](https://www.postgresql.org/docs/current/sql-truncate.html) and
[MVCC caveat](https://www.postgresql.org/docs/current/mvcc-caveats.html)
documentation. The API read barrier and bounded
queries serve this contract; implementation may add safe transaction locking
or choose another reset strategy without changing observable behavior.

## 16. DAA navigation and window API — settled

`levels.daa_score` is the DAA score of its current VSPC block, or `i64::MAX`
if that level has none. On new level creation use the sentinel, not zero.
Materializing a normal non-VSPC block does not set this score. The atomic
VSPC transaction sets/clears affected levels to their **final** values.
ApiService reaches the same final values from `VspcCommitted` vectors and
its cached block metadata; storage need not send a level-score delta.

For valid query `0 <= q < i64::MAX`, resolve a DAA target by current VSPC
floor, with the **highest level** among score ties:

```sql
SELECT level
FROM levels
WHERE daa_score <= $1
ORDER BY daa_score DESC, level DESC
LIMIT 1;
```

The sentinel is naturally excluded because no valid `$1` reaches MAX(i64);
an extra sentinel predicate is unnecessary. There may be VSPC-empty levels
after reorg. If q precedes the retained PP/no floor exists, report explicit
no-retained-match. q beyond the current VSPC DAA resolves the current VSPC
level. If q is at or above the DAA of HGC's lowest cached VSPC level, HGC
can resolve it; otherwise use an indexed DB lookup. Level resolution and its
window must come from **one immutable HGC image** or one consistent DB
transaction, never different revisions. Historical DAA/window response
caching is excluded from v2 and recorded for v2.1.

The public graph API has conceptually:

- head snapshot, depth-independent delta, and SSE cursor wakeup;
- one capped window operation with exactly one anchor: level, block hash, or
  DAA score; the anchor resolves once to a fixed level;
- status/info covering network, processing/API versions, node state, and
  current validated node server version.

Exact paths, methods, and final wire schema are implementation/API design
details. There is no `/blockHashesByIds`-style endpoint in v2 because every
graph response carries its hash dictionary. A window fully served by HGC has
a live cursor. A historical DB-backed window is a static image without a
cursor, capped by `MAX_WINDOW_DEPTH`. Requests crossing HGC's lower bound
take the consistent DB path; head depth itself never forces this fallback.

## 17. Web behavior — settled

The v1 Web's fast repeated polling is replaced by SSE cursor wakeups and
HTTP delta/snapshot catch-up for cached views. Head-following stays prompt.
For a fixed view, continue applying graph revisions **while its entire
window remains inside HGC**. Freeze the last coherent image once it slides
outside HGC; do not silently refresh/recenter it. A DAA request resolves
the DAA to a level at request time, then focuses on that level. If later
reorgs change that level's DAA, keep focus on the level—do not repeatedly
re-resolve the original DAA target. On GraphEpoch change, a head-following
view automatically reloads; a fixed view retains its coherent image marked
frozen/stale. Explicit refresh re-runs the original anchor query.

Fixed-view revision catch-up is distance-adaptive, not a blanket slow path.
Let `distance=max(0, head_level - visible_window_end_level)`. If head is
visible or at most ten levels ahead, update without added throttling. Beyond
that, delay increasingly as distance grows, while preserving contiguous
catch-up and snapshot fallback if delta retention expires. Exact delay
curve/cap is implementation work.

Web block identity is the hash; HTTP-local integers are decoded through the
response dictionary immediately. Do not use storage CompactIds in React
state, URL identity, or cross-response comparisons. Level/slot coordinates
are display positions, not global canonical identities.
When a materialized Genesis is present, Web recognizes it from its empty
actual direct-parent list. A pruned non-Genesis PP may have no visible
parent edge but still has actual direct parents; ORIGIN as selected parent
does not by itself mark Genesis.

## 18. Resource isolation and scalability — settled

The initial API is in-process, but the following **bulkheads are mandatory**:
separate capped read-only API DB pool from processing DB capacity; bounded
HTTP concurrency, query duration, response bytes/serialization CPU, SSE
clients/buffers, delta history, cache memory, and historical-read work.
Processing gets reserved connections/execution capacity and top priority.
API snapshot reload ranks above historical queries but below processing.
Status/info uses a separate memory-only admission lane so saturated graph
work cannot prevent clients from observing service state. Head delivery and
historical DB reads use distinct budgets.
On API saturation, reject/degrade API work explicitly; never block
processing, truncate a supposedly complete graph image, or silently drop a
processing notification. If all 1000 complete levels exceed API memory
allowance, drop an optional stale image first if useful, otherwise mark head
temporarily unavailable and retry complete reload. No partial levels.

SSE must coalesce wakeup cursors per slow client and disconnect persistent
laggards; no unbounded per-client queue. A few thousand concurrent clients
may require a separate stateless/read-only API deployment with suitable
cache/proxy and DB scaling later, but the in-process design does not forbid
that evolution. Do not start with multiple independent processors writing
the same database.
V2 exposes requests, latency, and response bytes by endpoint; active and
rejected SSE clients; cache hits/misses/evictions; DB permit and query time;
delta journal resets; slow-client disconnects; and block/VSPC commit latency.
API traffic up to configured rejection limits must not materially increase
BlockProcessor or VspcProcessor commit latency. Traffic-share estimates and
a numeric SSE limit are load-test inputs, not fixed architectural constants.

These are architectural invariants to make executable, not permission to

   `Unknown -> Present -> Removed` VSPC marker tracking, checked/decreasing

## 21. Rejected designs, to avoid accidental reintroduction

- No monolithic block+VSPC worker, committed-index waiters, placeholder block
  rows/promotion, or persistence of ordinary orphan-only hashes.
- No `Auto`, broad notification epochs, VSPC rewind/replay, source-blind
  notification-order commitment, or timer-based latecomer grace.
- No large `unordered_sink_capacity`/tenfold mergeset estimator, fixed X/Y
  GetBlocks rule for Catchup proximity/overlap, or “no unresolved orphan” Live
  prerequisite. Catchup primarily uses the rolling sink marker, VSPC
  membership state, and page-aware DAA threshold. Global-maximum position,
  normalized length `< 3`, and an empty VSPC page remain independent
  fallbacks. The later network-scaled page cap is a bounded body-tip coverage
  budget after ordinary Live eligibility, not a replacement Catchup trigger.
- No extra `ProcessingResources`, `ReadyAddedBlock`, or
  `PendingVspcChange` wrapper when `VspcChange` suffices.
- No removed-only VSPC destination fallback: pinned upstream sink selection
  cannot produce that regression. A notification violation requires Resync;
  a synthetic violation uses the bounded whole-attempt Retry policy. There is
  also no blanket rule that only ResyncEngine reconciliation may request
  Rebuild. A direct chain materiality fault and a resolver-confirmed
  unavailable dependency are explicit child Rebuild faults.
- No router enable before both remote subscriptions succeed. Callbacks
  during activation are intentionally dropped and receive no overlap credit.
- No immediate Live transition from overlap flags alone. Stop producing new
  synthetic VSPC messages and satisfy the fixed body-tip coverage invariant
  before global `EnteredLive`. VspcProcessor receives its existing Live command
  at ordinary eligibility; BlockProcessor remains in Catchup until coverage
  succeeds. No additional VSPC coverage phase is introduced.
- No parent-row FKs asserted merely because IDs exist; storage validates
  references transactionally. No dedicated persisted VSPC checkpoint table.
- No public CompactId, cross-instance coordinate identity assumption,
  partially populated HGC level, or API failure escalating to processing
  recovery solely because its observer feed was lost.
- No API read of a partially rebuilt DB, “catch SQL errors only” replacement
  for Reset, or Supervisor-owned PP/reconciliation preparation.
